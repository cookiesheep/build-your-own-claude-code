### 技术债务和已知问题

#### 后端

1. **`verifyUserToken` 只接受 `kind === 'anonymous'`**（`server/src/services/auth-token.ts:106`）
   - 密码登录用户通过 JWT cookie 认证，不走 Bearer token。这导致 `getOptionalAuthUser` 对 password 用户和 anonymous 用户走不同路径，逻辑分散。如果未来加 GitHub OAuth，需在 `verifyUserToken` 里也支持 `kind === 'github'`，或统一到 JWT cookie 方案。

2. **匿名用户没有过期清理机制**（`server/src/db/database.ts:313-332`）
   - `createAnonymousUser()` 只管创建，不管清理。长时间运行后 users 表会堆满匿名记录。`code_snapshots` 和 `user_progress` 也会挂在这些孤儿用户上。

3. **progress 表绑定 session_id 而非 user_id**（`server/src/db/database.ts:166-170`）
   - 已有 `user_progress` 表做 user 级追踪，`progress` 表是遗留设计。两个表同时存在增加维护负担，`progress.ts` 里的合并逻辑（第 38-46 行）是过渡性代码。

4. **sessionTokenCache 是进程内 Map**（`server/src/services/container-manager.ts:43`）
   - 重启后丢失所有 LLM proxy token，运行中的容器内的 ANTHROPIC_API_KEY 失效。`createContainer` 有重注入逻辑（第 316-341 行），但只在 session 有活跃容器时才触发。

5. **登录接口的 `DUMMY_PASSWORD_HASH`**（`server/src/routes/auth.ts:26`）
   - 这是标准的 timing-attack 防护手法。bcrypt 的 random salt 内置于 hash 中，硬编码 dummy hash 不构成安全风险——即使知道 dummy hash 也无法反推任何用户密码。此项非安全问题，无需修改。

6. **`injectCode` 已废弃但仍存在**（`server/src/services/container-manager.ts:394-424`）
   - 被 `injectFiles` 替代，但仍 export。应标记 deprecated 或删除。

7. **LLM proxy 没有请求体大小限制**（`server/src/routes/llm-proxy.ts:267`）
   - 全局有 1MB JSON body 限制（`index.ts:61`），但 `/api/llm/*` 路由代理的是任意 JSON body，大请求可能占用大量内存。

8. **`/api/reset` 和 `/api/environment/reset` 功能重复**（`server/src/routes/reset.ts` 和 `server/src/routes/environment.ts:221-279`）
   - 两个路由做完全相同的事情：removeContainer + createContainer。应合并为一个。

9. **container-cleanup 不清理 sessionTokenCache**（`server/src/services/container-cleanup.ts:236-263`）
   - `cleanupContainers` 删除容器后更新了 DB，但没有通知 `container-manager` 清理对应的 `sessionTokenCache`。被回收的容器对应的 token 会变成幽灵条目。

10. **LLM proxy 重启中断活跃用户会话**
    - 服务器重启时，运行中容器的 `ANTHROPIC_API_KEY` 立即失效。正在 TUI 中使用 Agent 的学习者会立刻遇到 LLM 401 错误，且没有任何前端恢复机制。这不是简单的"token 丢失"，而是生产环境中的用户可见中断。

11. **并发容器创建竞态**（`server/src/services/container-manager.ts`）
    - 用户快速双击"启动环境"可能触发两次 `createContainer`。`createContainer` 没有对同一 session 加锁，可能创建两个容器（第一个被第二个覆盖，成为孤儿容器）。

#### 前端

12. **labs.ts 中 Lab 1-5 全部 `enabled: false`**（`platform/src/lib/labs.ts:42-87`）
    - 只有 Lab 0 启用。`PlatformPageClient` 或 Lab 页面如何处理 `enabled: false` 需确认。

13. **`authorizedFetch` 的竞态条件**（`platform/src/lib/api.ts:157-192`）
    - 401 时自动续签匿名 token 并重试。如果 cookie auth 和 bearer token 同时存在，逻辑分支复杂，有潜在的请求倍增问题（一次失败最多发 5 个请求：原始→检查cookie→获取匿名token→重试→清token+重新获取+最终重试）。

14. **`file-reader.ts` 手动实现 auth 重试**（`platform/src/lib/file-reader.ts:34-73`）
    - 没有使用 `api.ts` 的 `authorizedFetch`，自己实现了一遍 401 → retry 逻辑，代码重复。

15. **前端 `User` 类型不完整**（`platform/src/lib/auth.ts:2-5`）
    - 只有 `id`, `username`, `role`，缺少 `kind` 字段。后端 `SessionUser` 也是如此（`session-cookie.ts:6-10`）。无法区分 password 用户和未来的 github 用户。

16. **`getWorkspace` 有 legacy 兼容逻辑**（`platform/src/lib/api.ts:525-536`）
    - 支持 `code: string` 旧格式，可删除。

17. **Lab 页面直接读文件系统**（`platform/src/app/lab/[id]/page.tsx:13-30`）
    - `readLabMarkdown` 用 `fs.readFile` 读 `../docs/labs/lab-XX/` 目录。这在 Vercel 等 serverless 环境下不工作，但当前部署在华为云自有服务器上，不影响使用。

## 二、GitHub OAuth 方案

### 技术选型

| 选项 | 优势 | 劣势 | 结论 |
|------|------|------|------|
| GitHub OAuth App | 注册简单，scope 精细 | 每个 repo 需单独授权 | 推荐 MVP |
| GitHub App | 权限更细，webhook 支持 | 配置复杂，审核流程长 | 后续考虑 |

**推荐：GitHub OAuth App**。只需要 `read:user` + `user:email` scope，足够获取 GitHub ID + 头像 + 昵称。

数据库已就绪。`users` 表（`database.ts:142-153`）已有：

- `username` TEXT — GitHub login
- `nickname` TEXT — GitHub display name

**无需修改 schema**，但需加一个查找函数：

#### Step 3: 匿名→GitHub 升级逻辑

这是核心难点。当匿名用户首次通过 GitHub 登录时：
1. 前端当前持有匿名 Bearer token（localStorage `byocc-auth-token`）
2. 用户点「GitHub 登录」→ 弹出 GitHub OAuth 窗口
3. 回调后，后端创建 `kind='github'` 的 user
4. 需要把匿名 user 的 `code_snapshots`、`user_progress` 迁移到 github user
5. 清除前端的匿名 token，用新 session cookie 替代

新增迁移函数（**必须在事务中执行**，防止部分失败导致数据不一致）：
```typescript
// database.ts
migrateUserData(fromUserId: string, toUserId: string): void {
  const db = this.db;
  const migrate = db.transaction(() => {
    const target = db.prepare('SELECT id FROM users WHERE id = ?').get(toUserId);
    if (!target) throw new Error(`Target user ${toUserId} not found`);

    // code_snapshots 主键是 (user_id, lab_number)
    // 如果双方都有同 lab 的 snapshot，UPDATE 会触发 UNIQUE 冲突
    // 解决：先用 INSERT OR REPLACE 合并，再删除源用户残留
    db.prepare(`
      INSERT OR REPLACE INTO code_snapshots (user_id, lab_number, code, updated_at)
      SELECT ?, lab_number, code, updated_at
      FROM code_snapshots WHERE user_id = ?
    `).run(toUserId, fromUserId);
    db.prepare('DELETE FROM code_snapshots WHERE user_id = ?').run(fromUserId);

    // user_progress 主键是 (user_id, lab_number)，同样需要 INSERT OR REPLACE
    db.prepare(`
      INSERT OR REPLACE INTO user_progress (user_id, lab_number, completed, completed_at)
      SELECT ?, lab_number, completed, completed_at
      FROM user_progress WHERE user_id = ?
    `).run(toUserId, fromUserId);
    db.prepare('DELETE FROM user_progress WHERE user_id = ?').run(fromUserId);

    // user_settings 主键是 user_id，直接 UPDATE 即可
    db.prepare('UPDATE user_settings SET user_id = ? WHERE user_id = ?').run(toUserId, fromUserId);

    // api_usage 有 user_id FK，也需要迁移
    db.prepare('UPDATE api_usage SET user_id = ? WHERE user_id = ?').run(toUserId, fromUserId);

    db.prepare('DELETE FROM users WHERE id = ?').run(fromUserId);
  });
  migrate();
}
```

#### Step 5: CSRF 防护

OAuth state 参数是防 CSRF 的标准做法：
- 发起时：`state = randomUUID()`，存入短期 httpOnly cookie `byocc_oauth_state`
- 回调时：比对 cookie 中的 state 和 URL 参数中的 state
- 不匹配则 403

#### 前后端接口设计

```
GET  /api/auth/github           → 302 重定向到 GitHub
GET  /api/auth/github/callback  → 302 重定向前端页面（设置 session cookie）
POST /api/auth/link-github      → 关联已有账户（可选，后续迭代）
```

### 安全考虑

1. **state 参数** — 必须使用 `crypto.randomUUID()`，存 httpOnly cookie，回调后立即清除
2. **client_secret** — 只在后端使用，永远不暴露给前端
3. **token 过期** — GitHub OAuth token 不过期（除非用户撤销），但 session cookie 有 7 天有效期
4. **redirect_uri 白名单** — 只允许配置中注册的回调 URL
5. **用户枚举** — 登录失败时不区分「用户不存在」和「密码错误」（已实现，`auth.ts:114-120`）
6. **rate limit** — `/api/auth/github/callback` 需要限流（可用现有 rate-limit 框架）

## 三、代码持久化现状分析

### 当前机制

**已实现完整的代码持久化**，这是一个做得很好的部分。

1. **Workspace 保存** — `PUT /api/labs/:id/workspace`（`workspace.ts:61-98`）
   - 前端每次代码变更后 1.5 秒自动保存（`LabRightArea.tsx:164-186`）
   - 保存到 `code_snapshots` 表（`database.ts:597-622`），以 `JSON.stringify(files)` 格式存储
   - 支持 file map（多文件 Lab）和单字符串（兼容旧格式）

2. **Workspace 恢复** — `GET /api/labs/:id/workspace`（`workspace.ts:35-59`）
   - Lab 页面加载时恢复（`LabRightArea.tsx:138-148`），与 skeleton 合并

3. **Submit 时也保存** — `submit.ts:79-80` 在注入容器前先 `saveWorkspaceSnapshot`

4. **跨 session 持久** — 数据绑定 `user_id`，不是 `session_id`。用户换浏览器（同一账号）可恢复代码。

5. **容器重置不影响代码** — `handleReset` 明确提示"当前草稿已保留"（`LabRightArea.tsx:316`）

### 缺失功能

1. **没有版本历史** — `upsertCodeSnapshot` 是覆盖写（`database.ts:607-614`）。如果学习者误删代码，无法回退。
   - 建议：新增 `code_snapshot_versions` 表，每次 PUT 时保留前一版。

2. **没有跨 Lab 代码复用** — 每个 Lab 的 workspace 独立存储。如果 Lab 3 基于 Lab 2 的完成品，需要前端手动处理合并。

3. **没有离线/断线恢复** — auto-save 1.5 秒，但如果网络断开，`saveState` 变成 `"error"` 后没有重试机制。`LabRightArea.tsx:176-180` 的 catch 只是设置 error 状态。

4. **匿名用户的代码丢失风险** — 匿名 user 的 token 在 localStorage 里，清浏览器数据就没了。GitHub OAuth 登录后如果迁移逻辑不完善，匿名时期的代码可能丢失。

5. **workspace 文件大小没有限制** — `workspace.ts:78` 的 `normalizeWorkspaceFiles` 只校验路径白名单，不校验单个文件内容大小。理论上可以提交很大的文件。

### 改进方案

| 改进 | 优先级 | 工时 | 说明 |
|------|--------|------|------|
| 断线自动重试 save | P0 | 2h | saveState="error" 后定时重试，恢复后标记 saved |
| 单文件大小限制（50KB） | P1 | 1h | `normalizeWorkspaceFiles` 加长度检查 |
| 版本历史（最近 10 版） | P2 | 4h | 新表 `code_snapshot_versions`，前端增加 diff 视图 |
| 跨 Lab 代码继承 | P2 | 6h | Lab N 加载时检查 Lab N-1 的 workspace |

**当前状态**：容器创建需要拉镜像、装依赖，首次可能要 2-3 分钟。前端只有一个"正在准备容器终端"的进度条（`Terminal.tsx:72-123`），估算 35 秒。

#### P1-3: 匿名用户清理机制

**当前状态**：匿名用户创建后永远不清理，users 表无限增长。

**需要做的**：

- 或者：匿名用户超过 N 天无活动，删除其数据

#### P1-4: sessionTokenCache 内存泄漏修复 + 重启恢复

**当前状态**：`container-manager.ts:43` 的 `sessionTokenCache` 是内存 Map。存在两个问题：

1. **运行时泄漏**（严重）：`container-cleanup.ts:246-248` 在回收容器时直接调用 `docker.getContainer().remove()`，绕过了 `container-manager.ts` 的 `removeContainer` 方法（该方法在 597-602 行清理 cache）。被回收的容器对应的 token 变成幽灵条目，永远不释放。
2. **重启丢失**（次要）：进程重启后所有 token 丢失，运行中容器的 LLM proxy token 失效。

**需要做的**：
- **修复泄漏**：`container-cleanup.ts` 必须调用 `container-manager.removeContainer()` 而非直接 `docker.remove()`。如果解耦需要，可以让 `removeContainer` 返回一个 cleanup callback 给 cleanup 模块调用。
- **重启恢复**：启动时扫描所有 running 容器，重新生成并注入 token（`createContainer:316-341` 已有部分逻辑，只需在 index.ts 启动时触发一次全量扫描）

**涉及文件**：
- `server/src/services/container-cleanup.ts:246-248`
- `server/src/services/container-manager.ts:43, 597-602`
- `server/src/index.ts`（启动时全量扫描）

#### P1-5: 构建日志展示优化

**当前状态**：`LabRightArea.tsx:292-293` submit 成功后只存 `buildLog` 字符串，展示在 Terminal 组件里。错误信息不够结构化。

**需要做的**：
- 构建成功时显示明确的"下一步：在终端输入 node cli.js"提示
- 构建失败时高亮错误行
- 考虑在 build log 下方加一个"重新提交"快捷按钮

#### P1-6: `verifyUserToken` 支持 github kind（从 P0 降级）

**当前状态**：`server/src/services/auth-token.ts:106` 硬编码 `if (payload.kind !== 'anonymous') return null`。

**为什么从 P0 降级**：密码登录用户通过 JWT cookie 认证，不走 Bearer token，当前不影响任何用户。仅在做 GitHub OAuth 时才需要扩展。作为 OAuth 的前置步骤归入 P1。

**需要做的**：
- 如果统一到 JWT cookie 方案（推荐），此函数只需也接受 `kind: 'github'`
- 或者全走 JWT cookie，废弃 Bearer token 路径中的 kind 检查

#### P1-7: 并发容器创建竞态防护

**当前状态**：`createContainer`（`container-manager.ts`）没有对同一 session 加锁。用户快速双击"启动环境"可能创建两个容器，第一个被第二个覆盖成为孤儿容器，浪费 2GB 内存。

**需要做的**：
- 在 `createContainer` 入口加 session-level 互斥锁（`Map<sessionId, Promise>`）
- 前端在请求期间禁用"启动"按钮（已有 `isLoading` 状态，确认是否覆盖了双击场景）

**涉及文件**：
- `server/src/services/container-manager.ts`
- `platform/src/components/LabRightArea.tsx`
