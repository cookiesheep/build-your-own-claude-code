## 一、当前已确认的机制

### 变体文件机制（已在用）

学习者通过 `-labN` 后缀的变体文件修改 claude-code-diy 源码：

```
claude-code-diy/src/
  components/LogoV2/
    Clawd.tsx          ← 原始文件（不动）
    Clawd-lab0.tsx     ← Lab 0 变体（学习者创建/修改）

build.mjs --lab=0
  → discoverLabSwaps() 发现 *-lab0.* 文件
  → 编译时替换原始文件的产物
  → 整个 416K 行系统一起编译
```

- Lab 0 已按此机制开发完成（6 个变体文件）
- 详细指南见：`D:/桌面2.0/BYOCC-Lab0-开发指南.md`
- PoC 已验证：`query-lab.ts`（~190 行）替换 `query.ts`（1,729 行）可行

## 二、核心待决问题

### 问题 1：Lab 1-3 用什么机制？

**两条路线**：

**路线 A：继续用变体文件机制**
- Lab 1: `query-lab1.ts` 替换 `query.ts`，学习者实现简化版 query 函数
- Lab 2: 在 Lab 1 基础上加工具执行逻辑
- Lab 3: 在 Lab 2 基础上加 while(true) 循环
- 优点：和 Lab 0 机制一致，已有 PoC 验证
- 缺点：学习者需要理解 416K 系统中 query.ts 的依赖链，入门门槛高

**路线 B：独立模块 + 依赖注入（LAB_DESIGN.md 建议）**
- Lab 1-3 在 `labs/lab-XX/` 下创建独立 TypeScript 模块
- 通过接口接收 LLMClient、ToolExecutor 等依赖
- 测试用 Mock，TUI 集成时才连接 claude-code-diy
- 优点：学习者代码独立可测，入门门槛低
- 缺点：和 Lab 0 的变体文件机制不一致，需要额外设计 bridge 代码

**路线 C：混合方案**
- Lab 0 用变体文件（品牌定制，不需要深度理解架构）
- Lab 1-3 用独立模块（核心编程，需要清晰的学习路径）
- 需要：设计独立模块如何与 claude-code-diy 的 query.ts 对接

**当前状态**：团队只理解变体文件机制，独立模块方案尚未想清楚怎么设计。**需要 Claude 深度参与设计。**

### 问题 2：评测怎么做？

**竞品对比**：

| 平台 | 测评方式 | 难度 |
|------|---------|------|
| CodeCrafters | 独立简化程序 → 输入 → 检查输出 | 简单 |
| BYOCC（变体文件） | 学习者的变体编译进 416K 系统 → 跑完整 CLI → ? | **困难** |

**三种评测层次**：

**Level 1：构建验证**（已有，后端 `POST /api/submit`）
- `build.mjs --lab=N` → exit code 0？
- 对 Lab 0 够用：能编译 = 格式没写错

**Level 2：冒烟测试**（需要开发）
- 构建成功后检查：
  - Lab 0: `grep "YOUR_BRAND" dist/` 确认占位符已替换
  - Lab 0: `node cli.js --version` 确认能启动
- 轻量级，不需要 Mock API

**Level 3：行为评测**（最复杂，需要设计）
- 在容器内起 Mock API 服务器
- `ANTHROPIC_BASE_URL=http://localhost:9999 node cli.js -p "test" --print`
- 检查 CLI 输出是否符合预期
- 需要：Mock API 服务器、响应场景设计、输出解析器

**关键技术验证点**：
- `--print` 模式在 claude-code-diy 里是否工作正常？（尚未验证）
- CLI 的 stdout 输出格式是什么？能否可靠解析？

### 问题 3：独立模块方案如何落地？

如果选择路线 B 或 C，需要设计：

1. **模块接口**：独立模块导出什么？怎么和 query.ts 的接口对齐？
2. **Bridge 代码**：独立模块如何被"注入"到 claude-code-diy 的构建流程中？
3. **测试框架**：vitest + Mock LLM 的基础设施
4. **教学递进**：从独立模块到真实系统的过渡如何设计？

**依赖**：这些设计决策影响评测方案、平台前端、Docker 镜像构建全链路。

## 三、平台"评测"Tab 的设计方向（已达成共识）

无论选择哪条技术路线，平台 UX 方向已确认：

- 终端区改为 **Tab 切换**：`[终端]` | `[评测]`

- 点击"评测"按钮时自动切到评测 Tab
- 测试全过后可切到终端 Tab 看运行效果
